# Развёртывание на сервере

Полная инструкция: от чистого VPS до работающего магазина, на котором
можно зарегистрироваться.

Домен и учётная запись у почтового провайдера **не нужны**. Сертификат
выпускается на IP-адрес, а письма печатаются в журнал воркера — оттуда вы
и возьмёте ссылку подтверждения.

## 1. Что понадобится

| Требование | Проверка | Примечание |
|---|---|---|
| Linux (Debian 12 / Ubuntu 24.04) | `cat /etc/os-release` | инструкция написана под них |
| 1 ГБ RAM минимум | `free -m` | обязателен файл подкачки, см. 2.3 |
| ~5 ГБ свободного диска | `df -h /` | образы занимают около 1.5 ГБ |
| Python 3.11 или новее | `python3 --version` | **важно**, см. ниже |
| `make`, `git`, `openssl` | `make -v; git -v; openssl version` | |
| Docker с плагином Compose v2 | `docker compose version` | v1 (`docker-compose`) не подойдёт |

**Про Python.** Скрипты настройки читают конфигурацию модулем `tomllib`,
появившимся в Python 3.11. На Ubuntu 22.04 стоит 3.10, и скрипты не
запустятся. Варианты: взять Ubuntu 24.04 / Debian 12, либо поставить
Python 3.11 отдельно.

## 2. Подготовка сервера

### 2.1. Отдельный пользователь вместо root

Работать под root не нужно ни на одном шаге.

```bash
adduser deploy
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh
cp ~/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
```

Дальше заходите на сервер как `deploy`.

### 2.2. Закрыть вход по паролю

Проверьте, что вход по ключу работает, **не закрывая текущую сессию**, и
только потом правьте `/etc/ssh/sshd_config`:

```
PermitRootLogin no
PasswordAuthentication no
```

```bash
sudo systemctl restart ssh
```

Перебор паролей по SSH — самая массовая атака на арендованные серверы.
После этой правки перебирать становится нечего.

### 2.3. Файл подкачки

**Это не рекомендация, а необходимость.** На 1 ГБ оперативной памяти
сборка образа и пики нагрузки упираются в потолок, и разница между
«медленно» и «сервер умер» — именно здесь.

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# уходить в подкачку только при реальной нехватке, а не заранее
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swap.conf
sudo sysctl -p /etc/sysctl.d/99-swap.conf
```

Проверка: `free -m` — в строке Swap должно быть около 2048.

### 2.4. Обновления и время

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y make git openssl curl
sudo timedatectl set-ntp true
timedatectl    # NTP service: active
```

Точное время важнее, чем кажется: по нему считается срок жизни ссылок из
писем и проверяется срок действия сертификатов.

### 2.5. Файрвол

```bash
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw enable
```

**Ловушка, о которой стоит знать.** Docker добавляет правила в `iptables`
в обход `ufw`. Опубликованный порт контейнера будет доступен снаружи,
даже если `ufw status` показывает «закрыто».

Нас это устраивает: наружу публикует порты только nginx (80 и 443). Ни
приложение, ни база данных, ни воркер портов не публикуют вовсе — они
живут во внутренних сетях с пометкой `internal`.

Но проверять фактическое состояние надо так, а не через `ufw status`:

```bash
sudo iptables -L DOCKER-USER -n
sudo ss -lntp | grep -E ':80|:443|:5432'
```

Порта 5432 в выводе быть не должно.

### 2.6. Освободить порты 80 и 443

```bash
sudo ss -lntp | grep -E ':80 |:443 '
```

Если там уже висит Apache или системный nginx — остановите:

```bash
sudo systemctl disable --now apache2 nginx 2>/dev/null
```

## 3. Установка Docker

Простой путь — из репозитория дистрибутива:

```bash
sudo apt install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
```

Либо официальный репозиторий Docker, если нужна свежая версия:

```bash
curl -fsSL https://get.docker.com | sudo sh
```

Дайте пользователю право работать с Docker без `sudo`:

```bash
sudo usermod -aG docker deploy
newgrp docker        # или просто перезайдите по SSH
```

Проверка:

```bash
docker version
docker compose version     # должно быть v2.x
```

Заодно ограничьте размер журналов Docker глобально — на маленьком диске
их переполнение роняет всё разом:

```bash
sudo tee /etc/docker/daemon.json >/dev/null <<'JSON'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
JSON
sudo systemctl restart docker
```

## 4. Доступность реестра образов

**Docker Hub недоступен с российских IP-адресов.** Проверьте до сборки:

```bash
docker pull hello-world
```

Если команда падает с ошибкой сети или таймаутом — нужен зеркальный
реестр. Есть два способа.

### Способ А: зеркало на уровне Docker (рекомендую)

Работает прозрачно, менять конфигурацию проекта не требуется.

```bash
sudo tee /etc/docker/daemon.json >/dev/null <<'JSON'
{
  "registry-mirrors": ["https://mirror.gcr.io"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
JSON
sudo systemctl restart docker
docker pull hello-world
```

Зеркала приходят и уходят, поэтому проверяйте, что выбранное работает.
Кандидаты помимо `mirror.gcr.io`: зеркала Яндекс Облака, Timeweb, Selectel
и других российских провайдеров — актуальные адреса смотрите в их
документации. Можно указать несколько, Docker переберёт по очереди.

### Способ Б: префикс реестра в конфигурации проекта

Если зеркало требует полного имени, впишите его в единый конфиг (шаг 6):

```toml
[project]
image_registry = "адрес-зеркала/"     # косая черта в конце обязательна
```

Префикс подставится ко всем трём образам: `nginx`, `python`, `postgres`.

## 5. Загрузка исходников

Проект будет жить в `/opt/selectashop`.

```bash
sudo mkdir -p /opt/selectashop
sudo chown deploy:deploy /opt/selectashop
```

### Вариант А: клонирование из Git (рекомендую)

Так обновления делаются одной командой `git pull`.

**Если репозиторий публичный:**

```bash
git clone -b claude/stage-0-infra --single-branch \
    https://github.com/1Shokoff/SelectaShop.git /opt/selectashop
```

**Если репозиторий приватный** — заведите на сервере ключ только для
чтения:

```bash
ssh-keygen -t ed25519 -C "selectashop-deploy" -f ~/.ssh/id_deploy -N ""
cat ~/.ssh/id_deploy.pub
```

Скопируйте вывод и добавьте его в GitHub: репозиторий → Settings → Deploy
keys → Add deploy key. **Галочку «Allow write access» не ставьте** —
серверу достаточно чтения.

```bash
cat >> ~/.ssh/config <<'CFG'
Host github-selectashop
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_deploy
    IdentitiesOnly yes
CFG
chmod 600 ~/.ssh/config

git clone -b claude/stage-0-infra --single-branch \
    github-selectashop:1Shokoff/SelectaShop.git /opt/selectashop
```

> Рабочая ветка называется `claude/stage-0-infra`. Если сольёте её в
> `main`, клонируйте без `-b`.

### Вариант Б: копирование с локальной машины

Годится, если сервер не должен ходить в GitHub.

Выполняется **на вашем компьютере**, не на сервере:

```bash
rsync -avz --delete \
    --exclude='.git' \
    --exclude='config/selectashop.toml' \
    --exclude='deploy/generated' \
    --exclude='__pycache__' \
    ~/путь/к/selectashop/ deploy@ВАШ_IP:/opt/selectashop/
```

Исключения здесь не случайны: `config/selectashop.toml` содержит секреты
вашего стенда, а `deploy/generated` — сертификаты и параметры, которые на
сервере должны быть свои.

Обратная сторона: без `.git` обновляться придётся тем же `rsync`.

## 6. Настройка

```bash
cd /opt/selectashop
make init-config
```

Команда создаёт `config/selectashop.toml` с правами `0600` и генерирует:
ключ подписи Django, пароли четырёх ролей базы данных, три
криптографических ключа и неугадываемый путь админки.

**Этот файл — единственное место, где что-либо настраивается.** Из него
берут параметры и Django, и nginx, и docker compose.

Откройте его и впишите **одно** обязательное значение:

```bash
nano config/selectashop.toml
```

```toml
[network]
server_ip = "ВАШ_IP"
```

Всё остальное имеет рабочие значения по умолчанию. При необходимости
поправьте:

| Параметр | Когда менять |
|---|---|
| `[project].image_registry` | Docker Hub заблокирован, см. шаг 4 |
| `[network].http_port` / `https_port` | порты 80/443 заняты |
| `[network].*_subnet` | подсети `172.28.x` пересекаются с вашей сетью |
| `[database.tuning].shared_buffers` | на сервере больше 1 ГБ памяти |
| `[email].backend` | `smtp` вместо `console`, см. шаг 11 |

Теперь сертификаты:

```bash
make tls-selfsigned     # для сайта, на IP-адрес
make db-cert            # для канала приложение <-> база
```

И генерация конфигураций:

```bash
make config
```

Команда проверяет конфигурацию и **отказывается работать** при опасных
сочетаниях: незаполненный IP, пустой или слабый ключ подписи, одинаковые
криптографические ключи, включённая админка без TLS, выключенный TLS при
настроенной базе данных. Если получили отказ — в сообщении написано, что
именно исправить.

## 7. Сборка и запуск

```bash
make build
```

Сборка занимает от 3 до 10 минут: скачиваются базовые образы и
устанавливаются зависимости Python. На 1 ГБ памяти она заметно опирается
на файл подкачки — если вы пропустили шаг 2.3, вернитесь к нему.

```bash
make up
```

Проверка состояния:

```bash
make ps
```

Должны быть четыре службы, и у `db` в колонке состояния — `healthy`:

```
NAME                  STATUS
selectashop-db-1      Up (healthy)
selectashop-nginx-1   Up (healthy)
selectashop-web-1     Up
selectashop-worker-1  Up
```

Первый запуск `web` дольше остальных: контейнер применяет миграции и
собирает статику. Смотреть можно так:

```bash
make logs
```

## 8. Создание владельца магазина

Владелец создаётся **только из терминала**. Веб-страницы «создать первого
администратора» не существует намеренно: у такой операции не должно быть
сетевой поверхности вообще.

```bash
make create-owner ARGS="--username ВАШ_ЛОГИН --email ВАША_ПОЧТА"
```

Пароль будет запрошен интерактивно, дважды. Адрес сразу помечается
подтверждённым, учётная запись активна.

Требования к паролю: не менее 10 символов, не похож на логин, не из
словаря распространённых, не только цифры.

## 9. Проверка работы

### 9.1. Базовые проверки

```bash
curl -kIs https://ВАШ_IP/healthz | head -1      # HTTP/1.1 200 OK
curl -Is  http://ВАШ_IP/        | head -2       # 301 -> https
curl -Is  https://ВАШ_IP/ -H 'Host: чужой.хост' # пустой ответ: соединение оборвано
```

Последняя проверка должна завершиться ошибкой соединения — это правильно.
Запрос с неизвестным заголовком `Host` обрывается без ответа, чтобы
отсечь сканеры, которые ходят по диапазонам IP вслепую.

### 9.2. Регистрация покупателя

Откройте в браузере `https://ВАШ_IP/accounts/register/`.

**Браузер покажет предупреждение о сертификате** — так и должно быть.
Сертификат самоподписанный, доверенного центра за ним нет. Нажмите
«Дополнительно» → «Перейти». Трафик при этом шифруется; предупреждение
исчезнет, когда появится домен и Let's Encrypt.

Заполните форму. Обе галочки согласия обязательны. После отправки увидите
страницу «Проверьте почту».

Теперь возьмите письмо:

```bash
make mail
```

В журнале воркера оно лежит целиком:

```
======================= ПИСЬМО (режим console) =======================
Кому:  buyer@example.com
Тема:  SelectaShop: подтвердите адрес почты
----------------------------------------------------------------------
...
https://ВАШ_IP/accounts/verify/xxxxxxxxxxxxxxxx/
```

Откройте ссылку и нажмите «Подтвердить».

> Кнопка нужна не для красоты. Корпоративные почтовые антивирусы сами
> открывают ссылки из писем, проверяя их на вредоносность. Если бы ссылка
> срабатывала при открытии, часть пользователей получала бы «ссылка
> устарела» ещё до того, как прочитала письмо.

Учётная запись активна. Войдите на `https://ВАШ_IP/accounts/login/` —
работает и логин, и адрес почты, регистр не важен.

### 9.3. Проверка роли администратора

Зарегистрируйте вторую учётную запись тем же способом и повысьте её:

```bash
make grant-role ARGS="ЛОГИН admin"
```

Роль меняется только так. Ни одна форма на сайте не принимает поле роли,
и администратор не может назначать администраторов — это может лишь
владелец из терминала.

Чтобы увидеть разницу в правах, включите админку Django:

```toml
[django]
admin_enabled = true
```

```bash
make config && make restart
```

Её адрес лежит в том же файле, в `[django].admin_url` — он сгенерирован
неугадываемым, чтобы боты не перебирали `/admin/`.

### 9.4. Проверка восстановления пароля

`https://ВАШ_IP/accounts/password-reset/` → указать адрес → `make mail` →
перейти по ссылке → задать новый пароль.

Обратите внимание: ответ одинаков для существующего и несуществующего
адреса. Иначе форма позволяла бы перебором выяснить, кто зарегистрирован
в магазине.

## 10. Уборка тестовых записей

```bash
# обезличивание: строка остаётся, данные человека удаляются
make delete-account ARGS="ЛОГИН --yes"

# полное удаление: строки не остаётся вовсе
make delete-account ARGS="ЛОГИН --hard --yes"
```

Без `--yes` команда попросит подтвердить, введя логин целиком.

Разница существенна. **Обезличивание** — боевой режим: строка
пользователя нужна, чтобы на неё ссылались будущие заказы, которые
придётся хранить для бухгалтерии. Адрес и логин при этом удаляются
физически и освобождаются для повторной регистрации. **Полное удаление**
возвращает базу в исходное состояние и годится только для тестовых
записей: вместе с пользователем исчезнет история его заказов.

Единственного владельца магазина удалить нельзя — команда откажет, чтобы
проект не остался без административного доступа.

Полный сброс базы, если хочется начать с чистого листа:

```bash
make down
docker volume rm selectashop_pgdata
make up
make create-owner ARGS="--username ... --email ..."
```

## 11. Подключение настоящей почты

Пока `[email].backend = "console"`, письма никуда не уходят — только в
журнал. Этого достаточно для проверки, но не для работы.

### 11.1. Проверьте, что хостер не закрыл исходящий SMTP

```bash
timeout 5 bash -c '</dev/tcp/smtp.yandex.ru/587' && echo открыт || echo закрыт
timeout 5 bash -c '</dev/tcp/smtp.yandex.ru/465' && echo открыт || echo закрыт
```

Многие российские хостеры закрывают исходящий SMTP по умолчанию для
борьбы со спамом и открывают по заявке в поддержку. Порт 25 закрыт почти
везде, и он нам не нужен.

### 11.2. Настройка

Пока домена нет, подойдёт личный почтовый ящик.

```toml
[email]
backend = "smtp"
from_address = "ваш.ящик@yandex.ru"
from_name = "SelectaShop"

[email.smtp]
host = "smtp.yandex.ru"
port = 465
user = "ваш.ящик@yandex.ru"
password = "пароль-приложения"
security = "ssl"
```

**Нужен пароль приложения, а не обычный пароль от ящика.** Он создаётся в
настройках безопасности почты. Если обычный пароль вдруг сработал —
значит, у вас отключена двухфакторная защита, и это стоит исправить.

Проверенные настройки:

| Провайдер | host | port | security |
|---|---|---|---|
| Яндекс | `smtp.yandex.ru` | 465 | `ssl` |
| Mail.ru | `smtp.mail.ru` | 465 | `ssl` |
| Gmail | `smtp.gmail.com` | 587 | `tls` |

```bash
make config && make restart
```

Проверка: запросите восстановление пароля и посмотрите `make mail` —
там будет либо отметка об отправке, либо понятная ошибка.

### 11.3. Ограничение этого режима

Письма уходят от вашего личного адреса, лимиты у бесплатных ящиков
жёсткие (сотни писем в сутки). Для боевой работы нужен домен: без него
невозможны ни собственный адрес отправителя, ни записи SPF, DKIM и DMARC,
без которых почта уходит в спам.

## 12. Обновление версии

```bash
cd /opt/selectashop
git pull
```

**Сверьтесь с шаблоном конфигурации.** Если в новой версии появились
параметры, `make config` сообщит об их отсутствии. Посмотреть, чего не
хватает:

```bash
diff <(grep -oE '^[a-z_]+ =' config/selectashop.example.toml | sort -u) \
     <(grep -oE '^[a-z_]+ =' config/selectashop.toml | sort -u)
```

Недостающие секции скопируйте из `config/selectashop.example.toml`
вручную — рабочий файл не перезаписывается автоматически, чтобы не
потерять ключи.

```bash
make config
make build
make up
```

Миграции применяются автоматически при старте контейнера `web`, ролью
владельца схемы. У роли приложения прав на изменение схемы нет, и это
намеренно.

## 13. Резервное копирование

### 13.1. Что копировать

Копий нужно **две**, и одна без другой бесполезна:

1. **База данных** — содержимое.
2. **`config/selectashop.toml`** — ключи шифрования.

Адреса почты хранятся в базе только в зашифрованном виде. **Потеря
`data_encryption_key` означает безвозвратную потерю всех адресов
пользователей**, даже при целом дампе базы. Храните копию конфигурации
отдельно от копии базы и в защищённом месте.

### 13.2. Снятие дампа

```bash
cd /opt/selectashop
make backup
```

Дамп ляжет в `backups/db-ГГГГ-ММ-ДД-ЧЧММ.sql.gz`. Снимается он ролью
только для чтения — она физически не может ничего изменить в базе.

Каталог `backups/` добавлен в `.gitignore`: дампы содержат персональные
данные, в репозитории им не место.

### 13.3. По расписанию

```bash
crontab -e
```

```cron
# дамп базы каждую ночь в 3:20, хранить 14 дней
20 3 * * * cd /opt/selectashop && make backup >/dev/null 2>&1 && find /opt/selectashop/backups -name 'db-*.sql.gz' -mtime +14 -delete

# чистка просроченных регистраций и старых записей журнала, раз в час
0 * * * * cd /opt/selectashop && make purge >/dev/null 2>&1
```

Обе команды рассчитаны на запуск без терминала.

### 13.4. Восстановление

Проверено: цикл «дамп → восстановление → расшифровка адресов» проходит
полностью, при наличии того же ключа шифрования.

```bash
cd /opt/selectashop

# 1. остановить приложение, чтобы никто не писал в базу
docker compose --env-file deploy/generated/.env stop web worker

# 2. залить дамп ролью владельца схемы
gunzip -c backups/db-2026-09-17-0320.sql.gz | \
  docker compose --env-file deploy/generated/.env exec -T db \
  psql -h /var/run/postgresql \
       -U "$(grep '^DB_OWNER_USER=' deploy/generated/.env | cut -d= -f2-)" \
       -d "$(grep '^DB_NAME=' deploy/generated/.env | cut -d= -f2-)"

# 3. поднять обратно
make up
```

Восстановление в **существующую** базу с теми же таблицами приведёт к
ошибкам «отношение уже существует». Восстанавливать следует либо в
пустую базу, либо предварительно удалив том:

```bash
make down
docker volume rm selectashop_pgdata
make up      # создастся пустая база со всеми ролями
# затем шаг 2 выше
```

## 14. Диагностика

### `make config` отказывается работать

Это штатное поведение: конфигурация проверяется и отклоняется при опасных
сочетаниях. В сообщении написано, что исправить. Самые частые случаи:
не заменён IP-адрес из шаблона, не созданы сертификаты (`make
tls-selfsigned`, `make db-cert`), выключен TLS при настроенной базе.

### Сборка падает на загрузке образов

Docker Hub заблокирован. Вернитесь к шагу 4.

### Сборка падает без явной ошибки, процесс «убит»

Не хватило памяти. Проверьте `free -m` — если подкачки нет, вернитесь к
шагу 2.3.

### Контейнер `db` не стартует при первом запуске

Он описан с `read_only: true` для защиты, и при первичной инициализации
тома это может помешать. Если в журнале (`docker compose logs db`) видны
ошибки записи, временно снимите ограничение: в `docker-compose.yml` у
службы `db` добавьте `read_only: false` после блока `<<: *hardening`,
поднимите систему, затем верните обратно — на уже созданном томе
ограничение не мешает.

### Сайт не открывается, порт занят

```bash
sudo ss -lntp | grep -E ':80 |:443 '
```

Остановите конфликтующую службу либо смените порты в `[network]`.

### Браузер ругается на сертификат

Так и должно быть, пока сертификат самоподписанный. Нажмите
«Дополнительно» → «Перейти». Исчезнет после перехода на домен и
Let's Encrypt.

### Письмо не приходит в режиме `smtp`

```bash
make mail
```

Воркер пишет туда причину отказа. Частые случаи: указан обычный пароль
вместо пароля приложения; хостер закрыл исходящий SMTP; адрес в
`from_address` не совпадает с ящиком, от имени которого разрешена
отправка.

Письмо не теряется: при ошибке оно откладывается с нарастающей задержкой
(1, 2, 4, 8, 16 минут) и после пяти неудач помечается отброшенным с
сохранением причины.

### Посмотреть, что в очереди

```bash
make psql
```

```sql
SELECT id, template_key, status, attempts, last_error
FROM notifications_outboxmessage
ORDER BY id DESC LIMIT 20;
```

### Полезные команды

```bash
make ps                  # состояние служб
make logs                # журнал всех служб
make mail                # журнал воркера рассылки
docker compose --env-file deploy/generated/.env logs db    # журнал базы
docker stats --no-stream # фактическое потребление памяти
make down                # остановить всё
```

## 15. Перед настоящим запуском

- **Купить домен** и перевести сайт на Let's Encrypt. Тогда исчезнет
  предупреждение браузера и можно будет включить HSTS
  (`[tls].hsts_seconds = 31536000`).

  Сейчас HSTS выключен намеренно. Сканеры безопасности советуют его
  включить, но с самоподписанным сертификатом он делает предупреждение
  браузера **непреодолимым** — кнопка «всё равно продолжить» исчезает, и
  вы потеряете доступ к собственному сайту.

- **Заполнить документы** в каталоге `legal/` и показать их юристу. Там
  заготовки с полями в угловых скобках, а не готовые документы.

- **Подать уведомление в Роскомнадзор** как оператор персональных данных
  и опубликовать политику обработки на сайте.

- **Настроить резервное копирование** по разделу 13 и хотя бы раз
  проверить восстановление из дампа. Непроверенная копия — это не копия.

- **Прогнать аудит безопасности**: `make audit`.

Устройство защиты, принятые решения и осознанно принятые риски описаны в
[SECURITY.md](SECURITY.md).
