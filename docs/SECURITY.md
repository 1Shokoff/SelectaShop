# Аудит безопасности — этап 0

Документ описывает принятые меры защиты, результаты проверок и осознанно
принятые риски. Обновляется на каждом этапе.

**Дата аудита:** 2026-09-17
**Объём:** nginx + Django, без базы данных, без аутентификации
**Целевая среда:** VPS 1 vCPU / 1 GB RAM, доступ по IP-адресу, без домена

---

Отдельно отмечу: проверка `gixy` на `alias_traversal` не сработала. Это
подтверждает, что директивы `alias` в блоках `/static/` и `/media/`
построены корректно и не позволяют выйти за пределы каталога.

Повторить всё разом: `make audit`.

### Дефекты, найденные и устранённые в ходе аудита

1. **Дублирование заголовков безопасности.** Заголовки выставляли
   одновременно nginx и Django, клиент получал по два экземпляра каждого.
   Для `X-Frame-Options` это не косметика: при нескольких экземплярах
   часть браузеров считает заголовок некорректным и перестаёт применять
   защиту от фрейминга. Устранено: копии от приложения снимаются через
   `proxy_hide_header`, единственным источником остаётся nginx. Настройки
   Django намеренно оставлены включёнными — если приложение когда-нибудь
   окажется доступно в обход nginx, оно защитит себя само.

2. **Утечка манифеста статики.** Файл `staticfiles.json` отдавался наружу
   и раскрывал полный перечень файлов проекта. Закрыт.

3. **Отсутствие `worker_rlimit_nofile`.** При `worker_connections 512`
   лимит дескрипторов оставался системным. Под нагрузкой это приводит к
   отказам `EMFILE`, поскольку на каждое клиентское соединение может
   приходиться второе — к приложению. Выставлено 2048, согласовано с
   `ulimits.nofile` в `docker-compose.yml`.

4. **Отсутствие CSRF-middleware.** Было исключено вместе с остальными
   подсистемами, зависящими от БД. Однако защита от CSRF работает на
   cookie и к базе не обращается — включена постоянно.

## 3. Меры защиты по уровням

### Изоляция контейнеров

| Мера | Назначение |
|---|---|
| `read_only: true` | корневая ФС недоступна на запись: полезную нагрузку после RCE некуда положить |
| `cap_drop: ALL` | ни одной linux-capability; оба сервиса работают от непривилегированных пользователей на портах выше 1024 |
| `no-new-privileges:true` | процесс не может повысить права, в том числе через setuid-бинарники |
| сеть `internal: true` | контейнер приложения не может инициировать соединение в интернет: ни выгрузить данные, ни скачать вторую стадию нагрузки |
| порты приложения не публикуются | Django достижим только через nginx |
| `mem_limit`, `cpus`, `pids_limit` | отказ локализуется в одном контейнере, а не выбирается OOM-killer случайно |
| `tmpfs` с `noexec,nosuid,nodev` | во временном каталоге нельзя выполнить файл |
| ротация логов (10 МБ на 3 файла) | переполнение диска логами — реальный сценарий отказа на малом VPS |
| непривилегированный образ nginx | мастер-процесс не запускается от root |
| код принадлежит root, приложению доступен только на чтение | процесс не может переписать собственные исходники |

### nginx

| Мера | Назначение |
|---|---|
| catch-all сервер с `return 444` | запрос с неизвестным `Host` обрывается без ответа |
| ограничение методов | всё, кроме `GET/HEAD/POST`, отбрасывается до Python |
| `limit_req` и `limit_conn` | защита от перебора и исчерпания соединений |
| таймауты заголовков и тела | защита от Slowloris |
| `client_max_body_size` | защита от раздувания тела запроса |
| белый список расширений в `/media/` | SVG исключён: это XML, он может содержать скрипт, и с нашего origin это хранимая XSS |
| блокировка точечных файлов и резервных копий | `.git`, `.env` и подобное недоступны |
| `server_tokens off` | версия не подсказывает, какие CVE пробовать |
| `X-Forwarded-For` равен `$remote_addr` | не `$proxy_add_x_forwarded_for`: иначе клиент подделал бы источник запроса и обошёл любую логику на основе IP |
| `absolute_redirect off` | внутренний порт 8080 не утекает в заголовок `Location` |
| `gzip_proxied` без ответов с cookie | защита от BREACH |

### Django

| Мера | Назначение |
|---|---|
| отказ старта при слабом `SECRET_KEY` | исключает тихий выезд в продакшен с ключом из шаблона |
| `ALLOWED_HOSTS` из конфига | защита от подмены `Host` |
| `USE_X_FORWARDED_HOST = False` | защита от host header injection в ссылках писем |
| Argon2id для паролей | рекомендация OWASP; PBKDF2 по умолчанию на порядок дешевле перебирать на GPU |
| минимальная длина пароля 10 | против словарного перебора |
| `HttpOnly` на обеих cookie | токен и сессия недоступны из JavaScript |
| `SameSite=Lax` | дополнение к CSRF-токену |
| строгая CSP без `unsafe-inline` | внешний скрипт не выполнится, даже попав в HTML через XSS |
| лимиты на число полей и размер формы | защита от DoS через разбор гигантских форм |
| отсутствие подсистем без БД | неработающий код не загружается вовсе |
| админка выключена и запрещена без TLS | при выключенном TLS пароль администратора шёл бы открытым текстом |

## 4. Принятые риски

### Риск 1: трафик не шифруется

**Статус:** принят на этапе 0, обязателен к устранению до этапа 1.

Сейчас `[tls].enabled = false`. Это допустимо ровно потому, что сайт не
передаёт ни паролей, ни сессионных cookie: аутентификации ещё нет.

С появлением формы входа риск становится неприемлемым: логин, пароль и
сессионную cookie будет видеть любой узел на маршруте. Домен для решения
не нужен:

```
make tls-selfsigned
# в config/selectashop.toml установить [tls].enabled = true
make config && make restart
```

Браузер покажет предупреждение — доверенного центра сертификации за
самоподписанным сертификатом нет, — но трафик будет зашифрован. Когда
появится домен, следует перейти на Let's Encrypt.

Защита устроена так, что забыть об этом нельзя: включение админки при
выключенном TLS блокируется на уровне генерации конфигурации.

### Риск 2: без домена невозможен доверенный сертификат

Центры сертификации не выдают публично доверенные сертификаты на
IP-адрес по обычной процедуре. Пока домена нет, вариантов два:
самоподписанный сертификат с предупреждением браузера либо открытый
трафик. Первый строго лучше второго.

### Риск 3: зависимости закреплены по версии, а не по хешу

`requirements.txt` фиксирует точные версии, но не контрольные суммы.
Это защищает от неожиданного обновления, но не от компрометации самого
индекса пакетов. Переход на `pip install --require-hashes` уместен,
когда состав зависимостей стабилизируется.

### Риск 4: nginx кеширует адрес приложения

nginx резолвит имя `web` один раз при старте. Если пересоздать только
контейнер приложения, он получит новый IP, а nginx продолжит обращаться
по старому. Поэтому `make restart` пересоздаёт оба сервиса вместе.
Отдельный `docker compose restart web` использовать не следует.

## 5. Не входит в этап 0

Появится на последующих этапах:

- **Этап 1:** TLS, аутентификация, строгий rate-limit на формы входа
  (зона `auth` уже описана в конфигурации), защита от перебора,
  журнал событий безопасности
- **Этап 2:** проверка загружаемых изображений по содержимому, а не по
  расширению
- **Этап 3:** шифрование ключей товаров в БД, выдача через
  `SELECT ... FOR UPDATE SKIP LOCKED`
- **Этап 4:** проверка подписи вебхуков, идемпотентность платежей
- **Этап 6:** резервное копирование БД, мониторинг, fail2ban или
  аналог на уровне хоста

## 6. Меры за пределами проекта

Настраиваются на самом VPS и в состав репозитория не входят:

1. **Файрвол.** Открыть только 22, 80 и 443. Docker вносит правила в
   `iptables` в обход `ufw` — проверять следует через `iptables -L -n`,
   а не через `ufw status`.
2. **SSH.** Запретить вход по паролю и вход для root, оставить только
   ключи.
3. **Swap.** Файл подкачки на 2 ГБ. На 1 ГБ RAM это разница между
   «медленно» и «сервер умер».
4. **Автоматические обновления безопасности** пакетов хоста.
5. **Регулярное обновление образов** и повторный прогон `make audit`.
